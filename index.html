What You'll Do

For each of 6 real Pull Requests from open-source projects, you will:

  1. Read the PR context — every PR starts with a short plain-language box explaining what the project is and what the change does (no knowledge of the project or of Python is needed). The code diff is available below it but collapsed by default — expand it only if you want to check a detail; the plain-language box gives you the intent.
  2. Read both AI-generated reviews side by side — Review A and Review B. You won't know which AI strategy produced which review. Judge only what each review actually says.
  3. Judge each review on 6 criteria — for every criterion, mark whether Review A does it better, Review B does it better, Both address it about equally, or Neither addresses it.
  4. Give one overall preference — after the 6 criteria, make a single holistic call: which review is more useful overall (or about the same).
  5. Briefly explain why in a text box (optional — one sentence is enough).
  6. Rate the difficulty of the comparison (1–5).

What makes a review more useful?

Imagine you are the author of the PR. A useful review:

  • Identifies specific problems or risks — not generic advice
  • Points to concrete code locations, file names, or function names
  • Explains why something is a problem, not just that it is
  • Mentions specific test files or test scenarios that should be covered
  • Covers the main issues without obvious gaps

Concrete example of the difference:

Vague (less useful)
"The test coverage may be insufficient for edge cases."		 Specific (more useful)
"The new test test_bayes.py:185 does not cover the fit_intercept=False path, so that variant goes untested."

You do not need deep knowledge of the codebase. Judge the review text itself: is it specific and grounded in the diff, or vague and generic?

Reading aids

Each review begins with a short summary of what that review claims. Where a review names a file, that file path is marked with a dotted underline — hover over it (or focus it with the keyboard) to see what we found about that file when we checked the project. These notes describe the file only; they do not say that the review is correct. You can optionally turn on highlighting to locate text unique to each review. Highlighting starts off, and naming more files is not automatically better.

Using the diff (optional)

The diff shows exactly what code changed. It is collapsed by default — you can judge the reviews without it. Expand it when you want to check whether a review describes a real risk in the changed code or a hypothetical one.

Tips

  • There are no right or wrong answers — we want your honest impression.
  • Some pairs will look similar. That's expected. Even a small but concrete difference counts.
  • If you're unsure, "no preference" is a valid answer — don't force a pick.
  • The "why" text box is optional, but even one sentence helps us understand your reasoning.

The 6 Criteria

Instead of one overall "who wins", you judge the reviews on 6 specific criteria. For each one you choose one of four: Review A does it better, Review B does it better, Both address it about equally well, or Neither addresses it at all.

Names the affected code Names concrete components, APIs, or design patterns affected by the change
Describes failure cases Describes concrete edge cases, boundary conditions, or error-handling gaps
Points to tests References concrete test files or says which tests should be added/updated
Explains why Gives a concrete reason for each suggestion (e.g. "X could cause Y")
Comments on code clarity Comments on code clarity, naming conventions, or function organization
Covers the important issues Covers the obvious issues in the PR without obvious gaps

Use Both and Neither freely — pick Both when the two reviews handle a criterion about equally well, and Neither when neither review addresses it. Only pick A or B when one is genuinely better for that specific criterion.

Problems found

The fetch() retry loop has no backoff between attempts, so a transient failure turns into a tight burst of requests against the upstream service.

Files and lines referenced

ApiClient.fetch(): the retry loop catches all RequestException subtypes including ConnectionError and Timeout, with no delay between attempts.

What could go wrong

Without backoff, rapid repeated requests could overwhelm the server or trigger rate limiting under transient failures.

Suggestions

Add exponential backoff (e.g. time.sleep(2 ** attempt)) between retries. Add tests in tests/test_api_client.py covering the exhausted-retries case.
